Changer de paradigme

Trois principes pour une architecture vivante

Traiter l'architecture comme du code : déclarative, multi-vues et intégrée au cycle logiciel.

01 · Vérité

Une unique source de vérité

Un modèle déclaratif centralisé et typé pour décrire le système sans ambiguïté.

  • Sémantique unifiée : éléments, rôles et relations qualifiés
  • Zéro redondance : chaque brique n'est définie qu'une fois, et réutilisée à l'infini en restant à jour

02 · Perspectives

Des perspectives multiples

Projeter plusieurs angles de lecture adaptés à chaque besoin depuis le même modèle.

  • Niveaux de détail : détailler le système de la vue d'ensemble macroscopique jusqu'aux briques internes
  • Filtrage ciblé : filtrer et projeter les composants selon l'enjeu et le public

03 · Cycle de vie

Un cycle de vie logiciel

L'architecture n'est plus un dessin figé : elle évolue au même rythme que le code.

  • Versionné dans Git : branches, historique et traçabilité partagée
  • Revue & CI/CD : diffs visuels en PR, validation et publication continue

Modélisation C4

Le modèle C4 : quatre niveaux pour hiérarchiser la composition de vos systèmes

  • C1 — Contexte Avec quoi interagit ce système ?
  • C2 — Containers Comment le système fonctionne-t-il ?
  • C3 — Components Comment se compose un container ?
  • C4 — Code Quelles classes / quels modules implémentent les composants ?
  • Dynamique Comment s'enchaînent les flux d'exécution et les scénarios d'usage ?
  • Déploiement Où tournent les conteneurs dans l'infrastructure réelle (zones, VM) ?
C4, c'est comme Google Maps :
un seul territoire, plusieurs niveaux de détail.
On ne dessine pas chaque niveau, on zoome dans un modèle unique.

V1 · la décision d'architecture

ADR-001 : digitaliser le stand café

ADR-001 Digital coffee.md
ADR-001 · Accepté

Le stand café numérique

Contexte

Le stand café d'AleFest souffre de 3 problèmes majeurs :

  • File d'attente saturée : 15 min d'attente, les festivaliers ratent des concerts
  • Zéro visibilité sur le temps et l'état d'avancement des commandes
  • Baristas débordés sans priorisation ni suivi des commandes

Décision

Créer un système de commande numérique au comptoir avec :

  • Borne / tablette pour saisir les commandes (staff ou festivalier)
  • Écran barista affichant la file de préparation en temps réel
  • Services découplés : Service Commandes + Service Préparation
  • File de messages RabbitMQ pour faire communiquer les backends
  • Base de données PostgreSQL pour la persistance des états et transactions

Contraintes & Conséquences

  • Validation barista en un tap (« commande prête »)
  • Le festivalier attend au comptoir jusqu'à remise de sa boisson (V1)
  • Pose une base simple et saine pour l'évolution mobile ultérieure (V2)

Rédiger du LikeC4 à la main est très rapide. Mais avec une décision formelle et structurée, un assistant IA peut générer le premier squelette de modèle sans faute de syntaxe en quelques secondes.

Socle commun · spécifications

Définir la grammaire de vos systèmes

LikeC4 ne vous impose pas un vocabulaire rigide : vous définissez la grammaire des systèmes de votre entreprise une fois pour toutes.

01 · Acteurs

Rôles & Personas

Qualifier qui interagit avec le système.

  • Actor_Person : utilisateur final, festivalier, client
  • Actor_Staff : barista, équipe d'exploitation interne
  • Forme et icônes dédiées pour les humains

02 · Typologie d'éléments

Systèmes, Conteneurs & Librairies

La nature et granularité de chaque brique du modèle.

  • System_New / System_External : frontières de domaines
  • Container_Spa / Container_Api : applications & services
  • Component / Library : briques internes, modules, SDKs
  • Container_Database / Queue : stockage & bus

03 · Sémantique des relations

Flux & Technologies

Zéro flèche anonyme, protocoles et modes d'échange explicites.

  • -[calls]-> + technology 'HTTPS' : appel synchrone bloquant
  • -[async]-> + technology 'AMQP' : événements découplés
  • -[writes]-> + technology 'SQL' : persistance transactionnelle
  • -[uses]-> : interaction humaine / expérience utilisateur

Zoom conteneurs (C2)

Illuminer la boîte noire : définir les applications et les services

Quels conteneurs permettent de composer l'expérience AleFest Coffee ?

01 · Frontends

Applications & Expérience

Les interfaces utilisateurs pour interagir au stand.

  • Counter App (SPA Comptoir) : prise de commande fluide pour festivaliers & staff
  • Barista Screen (SPA Écran) : file de préparation et priorisation en temps réel

02 · Services

Traitements & Asynchronisme

Le cœur de traitement découplé pour encaisser les pics de charge.

  • Order Service (API) : réception des commandes et calculs de prix
  • Preparation Service (API) : orchestration du flux de travail des baristas
  • File RabbitMQ (Queue AMQP) : découplage événementiel pour absorber les pics
  • Base PostgreSQL (Database) : persistance sécurisée des états et transactions

V1 · le diagramme

Le modèle s'enrichit par extension (C2)

model {
  extend alefestCoffee {
    // 1. Conteneurs internes du stand
    counterApp = Container_Spa 'Application Comptoir'
    baristaScreen = Container_Spa 'Écran Barista'
    orderService = Container_Api 'Service Commandes'
    preparationService = Container_Api 'Service Préparation'
    eventBus = Container_Queue 'RabbitMQ'
    database = Container_Database 'PostgreSQL'

    // 2. Flux synchrones, asynchrones & données
    counterApp -[calls]-> orderService 'POST /orders'
    baristaScreen -[calls]-> preparationService 'WebSocket'
    orderService -[async]-> eventBus 'Publie order.placed'
    eventBus -[async]-> preparationService 'Livre order.placed'
    orderService -[writes]-> database 'Commande'
    preparationService -[writes]-> database 'Statut'
  }
}
views {
  view c2_containers of alefestCoffee {
    title 'Coffee V1 - Containers'

    // Sélecteur Wildcard : tous les conteneurs d'alefestCoffee
    include alefestCoffee.*

    // Sélecteurs de relations : flux entrants & sortants
    include -> alefestCoffee
    include alefestCoffee ->

    // Sélecteur précis : flux direct vers le comptoir
    include festivalier -> alefestCoffee.counterApp
  }
}

V1 · Le comptoir

Système local,
festivalier captif

  • Commande numérique au comptoir via Application Comptoir
  • Responsabilités bien découpées entre commandes et préparation
  • La file de messages notifie seulement l'équipe de baristas
  • Le festivalier attend au stand jusqu'à la remise de la boisson

V2 · Le café mobile

Système intégré,
festivalier libéré

  • S'intégrer à l'app du festival + Service Festival pour commander à distance
  • Notification Service pour se libérer de l'attente au comptoir
  • Capitaliser sur la V1 : le socle événementiel s'étend aux notifications
  • Le café devient une expérience fluide, sans immobiliser le festivalier

coffee-v2/system-views.c4 
dynamic view order_mobile_flow {
  // 1. Commande mobile
  festivalier -> festivalSystem.festivalApp 'Commande un flat white'
  festivalSystem.festivalApp -> festivalSystem.festivalService 'POST /orders'
  festivalSystem.festivalService -> alefestCoffee.orderService 'POST /orders'
  alefestCoffee.orderService -> alefestCoffee.database 'INSERT order'
  alefestCoffee.orderService -> alefestCoffee.eventBus 'order.placed'
  festivalSystem.festivalService -> festivalSystem.festivalApp 'Confirme la commande'
  festivalSystem.festivalApp -> festivalier 'Commande confirmée'

  // 2. Préparation barista
  alefestCoffee.eventBus -> alefestCoffee.preparationService 'order.placed'
  alefestCoffee.preparationService -> alefestCoffee.baristaScreen 'WebSocket push file'
  alefestCoffee.baristaScreen -> barista 'Affiche commande'
  barista -> alefestCoffee.preparationService 'PATCH preparing'
  alefestCoffee.preparationService -> alefestCoffee.eventBus 'order.preparing'

  // 3. Notification & retrait
  barista -> alefestCoffee.preparationService 'PATCH ready'
  alefestCoffee.preparationService -> alefestCoffee.eventBus 'order.ready'
  alefestCoffee.eventBus -> alefestCoffee.notificationService 'order.ready'
  alefestCoffee.notificationService -> festivalSystem.festivalApp 'Push : votre café est prêt'
  festivalSystem.festivalApp -> festivalier 'Notification reçue'
  festivalier -> barista 'Récupère sa boisson'
}
✓ Les étapes s'appuient sur les identifiants réels du modèle : si un conteneur change de nom, la séquence est automatiquement mise à jour ou la CI lève une erreur.

Pourquoi LikeC4 ?

100% Open source,
zéro enfermement

  • Licences libres & pérennes : code ouvert sous licences permissives (MIT / Apache)
  • Indépendance totale : aucun abonnement cloud obligatoire, fonctionne 100% en local et dans vos runners CI/CD
  • Interopérabilité native : exports immédiats vers D2, PlantUML, Mermaid, PNG, JSON et app React autonome
  • Souveraineté de vos données : vos modèles restent sécurisés dans vos dépôts Git, sans fuite de secrets

Partage & dynamisme

Un écosystème vivant,
contributions bienvenues !

  • Packs & spécifications : partagez vos briques transverses (packs cloud AWS/GCP, conteneurs métiers, règles)
  • Outillage & IA : enrichissez l'extension VS Code, les serveurs MCP et les agents Copilot
